## 宿題
- 取り組んだレベル：基礎

- やったこと：
  `app/config.py` の `RAG_TOP_K` を5から3に変更し、ベクトル検索で返すページ数を減らした。検索件数以外は変更せず、同じ質問で回答内容や処理時間、トークン数、API費用を比較した。

- 比較した質問と、固定した条件：
  質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」

  使用モデル：`gemini-3.5-flash-lite`

  対象資料：第1〜3回の講義資料

- 結果：

  | 項目 | 変更前（5件） | 変更後（3件） |
  |---|---|---|
  | 回答 | 正しい | 正しい |
  | 引用ページ | 第2回PDF p.51、52 | 第2回PDF p.51、52 |
  | 実行時間 | 6.31秒 | 3.77秒 |
  | 入力トークン数 | 3,027 | 2,077 |
  | 出力トークン数 | 156 | 229 |
  | モデル応答回数 | 2回 | 2回 |
  | ツール呼び出し回数 | 1回 | 1回 |
  | 生成API推定費用 | $0.001298 | $0.001196 |

  変更前後ともに `search_materials` が1回呼び出され、検索語は「LoRA QLoRA 固定 学習」だった。

  LoRAについては、元の重みを固定し、低ランク行列を学習すると正しく回答した。QLoRAについても、4bit量子化を加えると正しく説明できていた。

- 改善した例と、残る失敗・制約：
  検索件数を減らしたことで入力トークン数が950減少し、生成APIの推定費用も減少した。今回の質問では、検索件数を3件にしても必要な根拠を取得でき、回答の正確さが維持された。

  一方で、検索件数を減らすと、複数ページに根拠が分散している質問では必要な情報を取得できない可能性がある。また、同じ条件で実行しても結果にばらつきがあるため、今回の測定だけで性能の優劣を断定することはできない。

- 気づき・疑問：
  検索件数を増やすことが必ずしも回答の品質向上につながるわけではなく、必要な情報を適切に取得することが重要だと分かった。今後は複数ページの情報を必要とする質問でも比較し、検索件数と回答精度の関係を確認したい。
